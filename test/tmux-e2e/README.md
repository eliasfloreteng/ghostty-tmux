# tmux control mode end-to-end tests (macOS)

These tests drive a real Ghostty.app through its AppleScript dictionary
(`macos/Ghostty.sdef`) and compare what the GUI shows with what tmux itself
reports over a private socket. They cover tmux control mode (`tmux -CC`):
tmux windows appear as native tabs, tmux panes appear as native splits, and
Ghostty UI actions are sent back to tmux.

The harness only looks at what the GUI shows from the outside, so it doesn't
depend on how control mode is implemented internally.

## Running

Requirements: macOS, [uv](https://docs.astral.sh/uv/), and `tmux` in `PATH`.

```sh
# Build the app first (emits zig-out/Ghostty.app, bundle id com.mitchellh.ghostty.debug)
zig build

# Run every scenario against zig-out/Ghostty.app
test/tmux-e2e/run.py

# Only some scenarios (substring match, repeatable)
test/tmux-e2e/run.py -k plumbing -k attach

# Another bundle, verbose step log, longer timeouts
test/tmux-e2e/run.py --app /Applications/Ghostty.app -v --timeout 20

# List scenarios
test/tmux-e2e/run.py --list
```

`run.py` is a uv script. uv installs its only dependency, `pyobjc`, into a
cached environment the first time you run it. The exit code is 0 if every
scenario passes or is skipped, 1 if any fails, and 2 if the run is aborted
(for example the app can't start or permission is denied).

The output directory (default `test/tmux-e2e/out/<timestamp>/`, gitignored)
holds `ghostty.log` (the app's stderr) and a screenshot of every Ghostty
window for each failed scenario.

## Isolation

- **tmux**: each scenario starts its own server via `tmux -L ghostty-e2e-<random>`.
  The config file is generated by the harness, so `~/.tmux.conf` is never
  read. Panes run `/bin/sh` with an empty environment and the prompt `$ `.
  The server is killed when the scenario ends, even if it failed.
- **Ghostty**: the bundle's executable (`Contents/MacOS/ghostty`) is started
  directly with `--config-default-files=false --config-file=<generated>`, so
  your Ghostty config is ignored. `TMPDIR` and `XDG_CONFIG_HOME` point into
  a temporary work directory. Ghostty's own terminals run a plain `/bin/sh`
  (prompt `gateway$ `). The instance is terminated at the end, also on
  failure or Ctrl-C.
- **AppleScript targeting**: Apple Events are addressed to the launched
  **process id** (`NSAppleEventDescriptor.descriptorWithProcessIdentifier`),
  not to the bundle identifier. This matters: `osascript`/JXA
  `Application(<pid>)` turns the pid back into a bundle id and can end up
  talking to _your_ running Ghostty instead. With raw events by pid, tests
  never touch another Ghostty instance, even one with the same bundle id.

The test app takes focus while it runs. It also briefly uses the
clipboard: reading screen contents puts a file path on the clipboard, and
the harness restores your previous clipboard _text_ afterwards.

## Permissions

- **Automation** (required): the first run triggers a macOS prompt asking
  whether your terminal may control Ghostty. If it was denied, the run
  aborts with error `-1743`. Allow it in System Settings → Privacy &
  Security → Automation.
- **Screen Recording** (optional): needed for useful failure screenshots.
- **Accessibility** (optional): lets `resize_window` resize the window
  through System Events. Without it, the scenario changes the font size
  instead, which also changes the grid size.

## What is checked

The terminal where `tmux -CC attach` is typed is the **gateway**. Every
other GUI tab is expected to belong to tmux:

| tmux                               | GUI (AppleScript)                       |
| ---------------------------------- | --------------------------------------- |
| window                             | tab (other than the gateway's)          |
| pane                               | terminal in that tab                    |
| `#{window_name}`                   | tab `name`                              |
| active window / pane               | tab `selected` / tab `focused terminal` |
| `#{window_width}x#{window_height}` | changes when the GUI is resized         |

To match GUI terminals to tmux panes, the harness types a unique marker into
each terminal (without Enter) and finds the pane whose `capture-pane` shows
it, then clears the line again.

Scenarios (see `e2e/scenarios.py`, or `--list`):

- `plumbing_*`: checks the harness itself (isolated launch, AppleScript,
  `input text`, reading the screen, the private tmux socket, a control
  client attaching). These should pass on any recent build, whether or not
  it supports control mode.
- `attach_existing_layout`: attach to a session with 2 windows (1 and 3
  panes).
- `tmux_*`: tmux-side changes show up in the GUI: `new-window`,
  `split-window`, `kill-pane`, `kill-window`, `rename-window`,
  `select-window`, `select-pane`, `resize-pane -Z`.
- `gui_*`: GUI-side changes show up in tmux: typing, `new_tab`,
  `new_split`, closing a split or tab, selecting a tab, focusing a split,
  `toggle_split_zoom`.
- `pane_output_visible`: output from `send-keys` appears on the GUI screen.
- `detach_client`, `server_exit`: the tmux tabs close, Ghostty keeps
  running, and the gateway shell still answers.
- `resize_window`: resizing the GUI changes the tmux window size.

Some things can't be checked automatically. These scenarios report `SKIP`
with a reason:

- `tmux_zoom_pane`: AppleScript exposes neither zoom state nor split
  geometry. The scenario saves a screenshot for a person to check.
- `gui_rename_tab`: the only rename action, `prompt_tab_title`, opens a
  dialog, so it can't be scripted.

## AppleScript notes

- AppleScript can't read terminal contents. The harness runs
  `perform action "write_screen_file:copy"`, which writes the screen to
  `$TMPDIR/<random>/screen.txt`. Because `TMPDIR` points to a private
  directory, the harness finds the file there and doesn't need to read the
  clipboard.
- The `terminal` class has `tty` and `pid`. Terminals backed by tmux panes
  may have no local tty, so the harness doesn't rely on these for tmux
  terminals.
- Window frames aren't scriptable. The harness reads them from CoreGraphics
  (`CGWindowListCopyWindowInfo`), which is also where it gets window ids for
  `screencapture -l`.

## Layout

```
run.py              CLI, runner, summary
e2e/appleevents.py  minimal Apple Event client (by pid)
e2e/ghostty.py      app launch/teardown, GUI snapshot, scripting commands
e2e/tmux.py         private tmux server, ground-truth queries
e2e/context.py      per-scenario fixture, GUI-vs-tmux comparison
e2e/scenarios.py    the scenarios
e2e/windows.py      CoreGraphics window list, screenshots, resizing
```

To add a scenario, write a function `def my_case(ctx: Context)` in
`e2e/scenarios.py` and decorate it with `@scenario`. The first line of its
docstring is what `--list` shows. Use `ctx.wait_synced()` or `wait_until()`
instead of `sleep`.
